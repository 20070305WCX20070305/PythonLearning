## 正文

### 3.1 docstring：写给未来的自己

docstring 是接口契约：说明"做什么、参数含义、返回什么、什么情况会报错、单位是什么"。
推荐 Google 风格，`mkdocstrings` 与 `napoleon`（Sphinx）都能解析：

```python
"""snr.py：信噪比计算。"""

import numpy as np


def compute_snr(signal: np.ndarray, background: np.ndarray) -> float:
    """计算脉冲信号的信噪比。

    约定：输入为计数数组，signal 与 background 的单位必须一致（counts）。

    Args:
        signal: 信号区间的计数，一维数组，不能为空。
        background: 本底区间的计数，一维数组，不能为空。

    Returns:
        信噪比，定义为 signal.mean() / sqrt(background.mean())。

    Raises:
        ValueError: signal 或 background 为空时。

    Examples:
        >>> compute_snr(np.array([100.0]), np.array([25.0]))
        2.0
    """
    if signal.size == 0 or background.size == 0:
        raise ValueError("signal 与 background 都不能为空")
    return float(signal.mean() / np.sqrt(background.mean()))
```

- 第一行一句话、祈使句，`help()` 里首先看到的就是它；
- 不写废话（"本函数返回结果"），写约束、单位、边界条件、副作用；
- 接口变化时同步更新 docstring——过期的文档比没有文档更糟。

**常见错误**

- 只写 `Args` 不写 `Returns` / `Raises`；
- 把实现细节写进 docstring（那是注释或设计文档做的事）；
- 中文 docstring 里的英文术语大小写混乱，读者无法确定哪个是参数名。

### 3.2 文档工具：MkDocs 与 Sphinx 怎么选

| 维度 | MkDocs（+ Material + mkdocstrings） | Sphinx |
| --- | --- | --- |
| 配置方式 | 单个 `mkdocs.yml`，简单直观 | `conf.py` + 目录结构，学习曲线陡 |
| 内容格式 | Markdown | reStructuredText 为主（也可用 MyST 写 Markdown） |
| 自动 API 文档 | mkdocstrings 直接读 docstring（Google 风格友好） | autodoc 最成熟、功能最全 |
| 交叉引用 / 多格式输出 | 较简单 | 强（PDF、man 等，适合大型库） |
| 适用场景 | 入门、以 Markdown 为主的项目 | 长期维护的大型类库、书籍式文档 |

**推荐：本阶段用 MkDocs + Material 主题 + mkdocstrings。** 上手快、和 Markdown 学习材料
一致；以后如果维护大型库、需要复杂交叉引用，再迁到 Sphinx（两者都读同一批 docstring，迁移成本不大）。

最小可用配置：

```yaml
# mkdocs.yml（放在项目根目录）
site_name: myproject
theme:
  name: material
plugins:
  - search
  - mkdocstrings:
      handlers:
        python:
          options:
            show_source: true
nav:
  - 首页: index.md
  - API 参考: api.md
```

```markdown
<!-- docs/index.md -->
# myproject

一句话说明这个项目做什么，指向 README 的安装说明。
```

```markdown
<!-- docs/api.md -->
# API 参考

::: myproject.cli
    options:
      show_root_heading: true
```

常用命令：

```bash
pip install mkdocs mkdocs-material "mkdocstrings[python]"
mkdocs serve        # 本地预览 http://127.0.0.1:8000，改文件自动刷新
mkdocs build        # 生成静态站点到 site/
mkdocs gh-deploy    # 发布到 GitHub Pages（推送到 gh-pages 分支）
```

文档站的最低标准：首页（项目是什么）、安装、最小使用示例、API 参考四块。

**常见错误**

- `mkdocs.yml` 放错位置（默认必须在项目根目录）；
- 忘了把 `site/` 写进 `.gitignore`，构建产物被提交；
- 链接大小写不一致：Windows 本地能开，Linux CI 上 404（文件系统区分大小写）。

### 3.3 pyproject.toml：一个文件管打包与工具配置

Python 打包从 `setup.py` 演化到 `setup.cfg`，现在是 `pyproject.toml`（PEP 518/621）。
一个典型模板（与 `项目-最终千行项目/模板/pyproject.toml` 一致）：

```toml
[build-system]
requires = ["setuptools>=64.0"]          # >=64 才支持可编辑安装（PEP 660）
build-backend = "setuptools.build_meta"

[project]
name = "myproject"                        # 发行名：pip install 用的名字
version = "0.1.0"                         # 语义化版本
description = "一个科研数据处理项目"
readme = "README.md"
requires-python = ">=3.10"
dependencies = []                         # 运行依赖；只用标准库时留空

[project.optional-dependencies]
dev = ["pytest>=7.0", "pytest-cov>=4.0"]  # pip install -e ".[dev]"

[project.scripts]
myproject = "myproject.cli:main"          # 安装后生成 myproject 命令

[tool.setuptools.packages.find]
where = ["src"]                           # src 布局

[tool.pytest.ini_options]
testpaths = ["tests"]
```

关键概念：

- **发行名 vs 导入名**：`project.name` 是 `pip install` 用的名字；`import` 的是
  `src/myproject/` 这个包目录名，两者可以不同但建议一致；
- **entry point / CLI**：`[project.scripts]` 把 `myproject` 命令映射到 `myproject.cli:main`，
  函数返回的整数会成为退出码；
- **src 布局**：源码放 `src/` 下，避免"在项目根目录运行测试时误导入当前目录"，强制通过安装使用。

常用命令：

```bash
# 开发安装：改代码立即生效，同时装 dev 组依赖
pip install -e ".[dev]"

# 构建分发包
python -m build                      # 生成 dist/*.whl 与 dist/*.tar.gz

# 验证并安装构建产物（换一个干净 venv 测试）
twine check dist/*
pip install dist/myproject-0.1.0-py3-none-any.whl
```

**常见错误**

- src 布局下忘记 `[tool.setuptools.packages.find] where = ["src"]`，装出来是空包；
- `pip install -e .` 在系统的 Python 里执行（应先激活 venv，否则污染全局环境）；
- `version` 在 `pyproject.toml` 与 `__init__.py` 各写一份且不同步（要么统一，要么用动态版本）；
- 依赖写得太宽（`pandas`）或太死（`pandas==2.1.0`），推荐折中（`pandas>=2.0`）。

### 3.4 版本号与发布

**语义化版本 MAJOR.MINOR.PATCH**：

- `PATCH`：修 bug，向后兼容（0.1.0 → 0.1.1）；
- `MINOR`：加功能，向后兼容（0.1.1 → 0.2.0）；
- `MAJOR`：不兼容的接口变化（0.9.0 → 1.0.0 也常表示"稳定了"）；
- `0.x` 阶段表示接口仍可能变；科研工具在 1.0 前每天改接口是常态，不必焦虑。

发布到 PyPI 的流程（了解即可，本阶段不实操）：

1. 在 TestPyPI 注册并练手，确认打包无误；
2. `python -m build` 得到 wheel 与 sdist；
3. `twine check dist/*` 检查元数据；`twine upload --repository testpypi dist/*` 上传测试；
4. 正式 `twine upload dist/*`（需要 API token，放在 `~/.pypirc` 或环境变量，绝不进仓库）。

实验室/内网场景更简单：把 `dist/*.whl` 发给同学，`pip install xxx.whl` 即可。
打 tag 记录版本：

```bash
git tag -a v0.1.0 -m "里程碑 1：骨架完成"
git push origin v0.1.0
```

**常见错误**

- 已发布的版本号被覆盖重传（PyPI 不允许同版本重复上传，必须递增版本）；
- token / 密码写进仓库或脚本；
- 打包时把测试数据、`.venv`、`__pycache__` 一起打进去（用默认规则 + 检查 `dist` 内容）。

### 3.5 性能分析：先测量，再优化

三条原则：

1. **不要猜瓶颈**：凭直觉优化的位置，十有八九不是热点；
2. **先正确，再快**：优化前先把测试写全，改坏了能立刻发现；
3. **记录数据**：优化前后各测一次，写下环境、样本、耗时、内存。

**timeit**——微基准，测小段代码：

```python
import timeit

# 方式一：代码里调用
t = timeit.timeit("sum(x * x for x in range(1000))", number=1000)
print(t)  # 1000 次的总耗时（秒）

# 方式二：命令行（-s 是准备代码）
# python -m timeit -s "import numpy as np" "x = np.arange(10000); x * x"
```

注意：单次 `time.time()` 测出的数不可信（受系统负载、缓存影响）；
`timeit` 自动重复多次取最小值，更接近真实性能。

**cProfile + pstats**——函数级 CPU 分析：

```bash
# 把整个脚本的分析结果写到 profile.out
python -m cProfile -o profile.out scripts/run_pipeline.py data/raw

# 交互式查看
python -m pstats profile.out
# 提示符下输入：
#   sort cumtime
#   stats 20
#   quit
```

也可以在代码里对单个函数分析：

```python
import cProfile
import pstats

cProfile.run("run_pipeline('data/raw')", "profile.out")
pstats.Stats("profile.out").sort_stats("cumtime").print_stats(15)
```

读结果：`cumtime` 是"包含子调用"的累计时间，`tottime` 是函数自身耗时；
二者差距大的函数说明时间花在它调用的东西上，继续往下钻。

**tracemalloc**——内存分配分析：

```python
import tracemalloc

tracemalloc.start()
data = load_big_table("data/raw/big.h5")
snapshot = tracemalloc.take_snapshot()

for stat in snapshot.statistics("lineno")[:5]:
    print(stat)  # 按分配位置列出内存占用，前 5 名就是优化线索
```

**py-spy**——采样式分析器，开销小、能附加到正在运行的进程：

```bash
pip install py-spy
py-spy top -- python -m myproject run config.toml   # 类似 top 的实时视图
py-spy record -o profile.svg -- python ...          # 生成火焰图
```

适合"长时间运行的流水线到底卡在哪"这类问题；日常微优化仍用 `timeit`/`cProfile`。

**优化案例：阶段 02 的批处理脚本**

症状：处理 500 个 CSV（共约 2 GB）耗时 20 分钟。

第一步，测量：`cProfile` 显示 70% 时间在 `pandas.read_csv`，清洗计算只占 10%。

第二步，分析：读 CSV 主要是 IO 等待与解析，属于"等待型"工作；清洗是 CPU 计算。

第三步，按类型选择手段：

| 问题 | 手段 | 预期收益 |
| --- | --- | --- |
| CSV 解析慢 | 传 `dtype`、`usecols`、指定 `engine="c"` | 解析量减半，明显加速 |
| IO 等待 | `concurrent.futures.ThreadPoolExecutor` 并发读多个文件 | 等待重叠，提高吞吐 |
| CPU 清洗 | `ProcessPoolExecutor`（阶段 02 的 multiprocessing） | 吃满多核 |
| 循环里拼 DataFrame | 先收集结果列表，最后一次 `pd.concat` | 避免 O(n^2) 复制 |
| 重复处理 | 记录文件哈希/状态，跳过已处理文件 | 总量直接下降 |

第四步，复测：耗时从 20 分钟降到 6 分钟；记录到项目文档里。

**常见错误**

- 用 `time.time()` 单次测量就下结论（噪声比优化收益还大）；
- 在循环里逐行拼接 DataFrame / 字符串（`concat` 应放在循环外）；
- 过早优化：3 秒的脚本优化到 1 秒，却牺牲了可读性；
- 优化后没跑测试，结果"快了但算错了"；
- 把内存问题当成 CPU 问题：明明 `MemoryError`，却在优化 CPU 计算。

## 练习

1. **补全 docstring**：给你项目里所有公开函数/类补 Google 风格 docstring。
   提示：先模块层、再类与 `__init__`、最后其他方法；单位与异常最重要。
   验收：`python -c "import 包; help(包)"` 输出结构完整。

2. **搭建文档站点**：用 MkDocs + Material + mkdocstrings 生成文档，含首页、安装、API 三页。
   提示：API 页用 `::: 包名.模块名`；标题层级会影响右侧目录。
   验收：`mkdocs build` 无警告；`mkdocs serve` 本地可浏览 API。

3. **打包并下游使用**：把你的小包用模板打包，在新终端里从**其他目录**调用 CLI。
   提示：确认 `[project.scripts]` 入口函数签名是 `main(argv=None) -> int`。
   验收：`pip install -e ".[dev]"` 成功；`你的命令 --help` 在任意目录可用。

4. **版本与 tag**：为项目打 `v0.1.0` 标签，写一段 CHANGELOG。
   提示：`git tag -a v0.1.0 -m "..."`；CHANGELOG 写"新增/修复/变更"三块。
   验收：`git tag` 能看到标签，`git show v0.1.0` 能看到消息。

5. **性能优化报告**：用 cProfile 找出项目里最慢的函数，至少优化一处。
   提示：先写性能测试脚本（固定样本、重复 3 次取中位数），再改代码。
   验收：提交一份对比说明：环境、样本、优化前后耗时/内存、为什么有效。
