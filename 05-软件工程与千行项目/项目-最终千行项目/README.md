# 最终千行项目

这是阶段 05 的收官之作：一个 **1000 行以上、有测试、有文档、能打包安装** 的科研软件项目。
从下面三个候选题目中选一个，先通读三份需求书，再用"如何选择"一节的方法做决定。

> 本项目不是"再写一个大脚本"。验收看的是工程完整度：
> 模块划分、测试、CI、文档、打包、可复现。

## 候选 A：实验数据自动化流水线

### 背景

实验室仪器每天产出大量 CSV / 文本 / 二进制文件（光谱、示波器波形、计数器日志等），
人工重复"复制 → 清洗 → 画图 → 汇总"既费时又易错。你需要一个可以持续运行的本地工具，
自动完成从原始文件到报告的全流程。

### 功能需求

MVP（必须完成）：

- [ ] 监控输入目录（轮询即可，不要求文件系统事件），发现新文件后加入处理队列；
- [ ] 并行解析多种格式（至少 CSV + 一种二进制格式：HDF5 或 SQLite）；
- [ ] 清洗：统一列名与单位、处理缺失值、按规则剔除异常点；
- [ ] 结果写入 SQLite（结构化指标）与 HDF5（原始曲线归档）；
- [ ] 自动生成图表（matplotlib）与 Markdown 报告；
- [ ] CLI：`run`（处理一次）、`watch`（持续监控）、`report`（重新生成报告）；
- [ ] 日志写文件；处理失败的文件进入"死信目录"，日志能定位原因。

进阶（有余力再做）：

- [ ] 全部路径与阈值由配置文件（TOML/JSON）驱动；
- [ ] 幂等性：同一文件重复处理不产生重复记录（文件哈希 + 状态表）；
- [ ] 失败自动重试 N 次，退避等待；
- [ ] 进度条（tqdm）与运行统计；
- [ ] 每日汇总报告。

### 涉及技术

| 阶段 | 用到的技术 |
| --- | --- |
| 01 | 目录扫描、路径处理、argparse、logging、venv、Git |
| 02 | pandas 清洗、HDF5、SQLite、multiprocessing/线程池、psutil、tqdm |
| 05 | 类设计（Source/Pipeline/Sink）、pytest、CI、pyproject 打包、MkDocs |

### 难点

- 进程池与 SQLite 并发写入：建议每个子进程只解析并返回结果，由主进程统一入库；
- 幂等与崩溃恢复：用状态表记录 `file_hash / status / attempts`，重启后继续；
- 清洗规则的正确性：单位换算、异常点判定必须有已知样本做测试。

## 候选 B：远程计算任务管理器

### 背景

你经常要在集群上提交成百上千个小任务（参数扫描、批量拟合）。手动 `ssh` 提交、
`squeue` 查看状态、`rsync` 取回结果非常繁琐，也容易漏掉失败的任务。
你需要一个本地管理工具：把任务清单变成可追踪的状态表。

### 功能需求

MVP：

- [ ] 从配置文件 / CSV 读取任务清单（命令、参数、资源需求）；
- [ ] 抽象后端接口 `Backend`，包含 `submit / status / fetch / cancel` 四个方法；
- [ ] 至少两个实现：`LocalBackend`（本机 subprocess，开发和测试用）与
      `SlurmBackend`（SSH + `sbatch` / `squeue`）；
- [ ] 轮询任务状态并记录到 SQLite（状态机：`pending → running → done / failed`）；
- [ ] 失败自动重试（限制次数、指数退避）；
- [ ] 用 `rsync` 归档结果目录并生成汇总表；
- [ ] CLI：`submit` / `status` / `collect` / `retry`。

进阶：

- [ ] 任务依赖（DAG：A 完成后才提交 B）；
- [ ] 并发提交与并发上限（同时运行的任务数）；
- [ ] `--dry-run` 干跑模式，打印将要执行的命令；
- [ ] 失败汇总报告（写文件即可）。

### 涉及技术

| 阶段 | 用到的技术 |
| --- | --- |
| 02 | subprocess、线程/异步、SQLite、tqdm |
| 03 | 进程、退出码、信号、超时 |
| 04 | SSH、rsync、Slurm、环境模块、Apptainer 命令 |
| 05 | 抽象基类与多态后端、依赖注入、Mock 测试、CI（用 LocalBackend 无需集群） |

### 难点

- 可测试性：测试绝不能真连集群——把所有"系统调用"隔离进 Backend 实现，
  单元测试注入假后端，这是本项目最重要的工程训练；
- 状态机与幂等：重复轮询不重复归档，进程重启后能接着跑；
- SSH 的失败模式：超时、认证失败、连接复用，都要有明确的错误分类与日志。

## 候选 C：科研数据归档与检索系统

### 背景

多年的实验数据散落在多个硬盘与目录里，命名风格不一，想找"2024 年 3 月测的、束流能量
在某个区间的数据"只能靠记忆。你需要一个本地数据目录：扫描 → 建元数据 → 搜索 → 导出。

### 功能需求

MVP：

- [ ] 扫描数据目录，提取元数据（路径、大小、mtime、类型、从文件内容提取的关键物理量）；
- [ ] 计算文件哈希（大文件可用"大小 + 首尾采样"近似）用于唯一标识与去重提示；
- [ ] 元数据与标签存 SQLite（设计好 schema）；
- [ ] 增量扫描：用 `mtime + size` 跳过已扫描文件；
- [ ] 搜索：按标签、文件名关键字、时间范围、物理量范围组合过滤；
- [ ] 导出：把搜索结果复制/打包到目标目录，附 manifest（CSV 或 JSON）；
- [ ] 版本记录：同一逻辑数据集的多次测量可关联（`parent_id` 或 group 标签）；
- [ ] CLI：`scan` / `tag` / `search` / `export`。

进阶：

- [ ] SQLite FTS5 全文搜索（文件名与注释）；
- [ ] 重复文件检测报告；
- [ ] 元数据提取插件化（不同仪器不同提取器——天然的多态场景）；
- [ ] HTML 版搜索结果报告。

### 涉及技术

| 阶段 | 用到的技术 |
| --- | --- |
| 01 | 文件系统遍历、路径处理、SQLite、logging、argparse |
| 02 | pandas、HDF5 读取、哈希与 IO、tqdm |
| 05 | 提取器多态（OOP）、pytest、CI、打包 |

### 难点

- schema 设计：数据表、标签表、关联表的规范化，以及未来加字段的扩展性；
- 大目录扫描性能：IO 密集，考虑跳过规则、批量事务提交；
- 物理量提取的正确性：不同仪器格式要用少量真实样本做回归测试。

## 如何选择

| 维度 | A 流水线 | B 远程任务 | C 归档检索 |
| --- | --- | --- | --- |
| 需要外部环境 | 无（本机即可） | 有集群更好（无则用 LocalBackend） | 无 |
| 可测试性 | 中（并发与 IO 多） | 高（后端抽象后全是纯逻辑） | 高（IO + SQL） |
| 算法含量 | 中 | 低-中 | 中（匹配与检索） |
| 展示效果 | 强（图表、报告） | 中（状态表） | 强（搜索演示） |
| 与真实科研的贴近度 | 高 | 高 | 高 |
| 主要工程训练 | 并发 + 幂等 + 数据正确性 | 抽象设计 + 状态机 + 可测试性 | 数据建模 + 性能 |

建议：

- 手头有真实数据或实验组需求：选 A，最容易做出"真的有人用"的东西；
- 经常跑集群、被提交作业折磨过：选 B，工程味最浓，最能体现"接口/多态/测试替身"；
- 数据多且乱，或想练数据库与检索：选 C，外部依赖最少，最容易稳妥交付；
- 拿不定主意：选 C（无外部依赖、测试容易、能稳定拿到完整验收）。

## 架构设计模板

分层（从上到下，依赖只能向下）：

1. **接口层**（`cli.py`）：解析参数、调用服务、格式化输出；不写业务逻辑。
2. **服务/领域层**（`services/`、`models.py`）：核心逻辑与数据结构，不 import CLI。
3. **数据访问层**（`io/`、`backends.py`、`db.py`）：文件、数据库、SSH 等外部世界的隔离层。
4. **横切关注点**（`config.py`、`logging_utils.py`）：被各层使用。

模块划分参考（以流水线为例）：

| 模块 | 职责 | 不应包含 |
| --- | --- | --- |
| `cli.py` | 参数到调用的映射 | CSV 解析逻辑 |
| `config.py` | 读取与校验配置 | 业务默认值 |
| `io/parsers.py` | 格式 → DataFrame | 清洗规则 |
| `services/cleaning.py` | 清洗规则 | 数据库写入 |
| `services/pipeline.py` | 组装流程、编排 | argparse |
| `io/storage.py` | 写 SQLite/HDF5 | 统计计算 |
| `reports/` | 图表与报告生成 | 文件解析 |

统一约定：

- 配置：`@dataclass` + TOML/JSON，全部路径可配置；
- 日志：`logging`，控制台 INFO、文件 DEBUG，关键步骤有日志；
- CLI：`argparse` 子命令（不引入第三方 CLI 框架）；
- 错误：预期错误抛带信息的异常，CLI 顶层捕获并记录，不裸抛 Traceback。

## 里程碑模板

| 里程碑 | 时间 | 交付内容 | 判定标准 |
| --- | --- | --- | --- |
| M1 骨架 | 第 10 周 | 需求书、目录结构、配置/日志/CLI、CI | `--help` 可用；CI 绿 |
| M2 MVP | 第 13 周 | 全部 MVP 功能、核心测试 | 端到端跑通样本；覆盖率 >= 70% |
| M3 交付 | 第 16 周 | 文档、打包、演示、tag | 新 venv 可安装；README 可复现 |

每个里程碑写一段"交付说明"：做了什么、怎么运行、已知限制、下一步计划。

## 验收标准模板

- [ ] 代码量 >= 1000 行（不含第三方与自动生成代码），无超大单文件；
- [ ] 在新 venv 中 `pip install -e ".[dev]"` 成功；
- [ ] `myproject --help` 与至少 3 个子命令可用；
- [ ] `pytest` 全绿；核心模块覆盖率 >= 70%；
- [ ] CI 在 Python 3.10 / 3.11 / 3.12 上全部通过；
- [ ] README 含一句话简介、安装、使用示例、目录结构、开发说明；
- [ ] `mkdocs build` 成功，公开接口都有 docstring；
- [ ] 提供示例数据或生成脚本，一条命令能复现端到端流程；
- [ ] 无硬编码绝对路径；换配置即可换输入/输出位置；
- [ ] 出错时有清晰日志与退出码，不出现裸 Traceback。

## 如何用 Git 管理开发过程

- **分支**：`main` 始终可运行；开发用 `feat/xxx`、修复用 `fix/xxx`，合并前 CI 必须绿；
- **commit 规范**（简化版 Conventional Commits）：
  - `feat: 支持 HDF5 解析器`
  - `fix: 修复空文件导致崩溃`
  - `test: 补充剔除规则的边界用例`
  - `docs: 更新安装与使用说明`
  - `refactor: 抽出 Parser 基类`
  - `chore: 更新 CI 配置`
- **tag**：每个里程碑打一个：`git tag -a v0.1.0 -m "M1 骨架"`，最后 `v1.0.0`；
- **待办**：用 GitHub Issues 或仓库里的 `TODO.md` 记录；大改动先写设计（几行字）再动手；
- **习惯**：每次开始工作先 `git status`，收工前提交并 push；提交粒度是"一件完整的小事"。
